Remarks

Every change returns a new registry, as .NET's immutable collections do. Default holds QuantLib's known factors between its petroleum units, which its manager holds at start and after clear(), with two of them stored the right way round: QuantLib stores one litre as worth 3.78541 gallons and one gallon as worth 42,000 thousand-barrels (unitofmeasureconversionmanager.cpp:115-122), where one gallon is 3.785 411 784 litres and, "by custom", 42 gallons a barrel (NIST Handbook 44, Appendix C), so a direct lookup converts 1,000 litres into 3,785.41 gallons there and 264.17 here (Divergences/CommodityKnownFactorsTests.cs). Add(UnitOfMeasureConversion) replaces a conversion of the same commodity type between the same two units, either way round, and puts the new one last, as QuantLib's add does.

Lookup(CommodityType, UnitOfMeasure, UnitOfMeasure, UnitOfMeasureConversionType) finds a direct, triangulated or chained conversion in QuantLib's order. QuantLib's chained search forbids each unit it starts from to the searches below it, to avoid cycles, but drops the list when it recurses (:190), so a search whose first candidate leads back recurses without end: its known factors' first entry pairs thousand-barrels and barrels, so every chained search from either overflows the stack (barrels to metric tonnes, with or without a path). Here the list is passed down, as QuantLib's ExchangeRateManager passes its own; wherever QuantLib's search returns it never revisits a unit above it, so the answer is QuantLib's (Divergences/UnitConversionSearchTests.cs).

Two registries are equal when they hold equal conversions in the same order; the hash is computed when the registry is built.
