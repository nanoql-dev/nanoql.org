Remarks

A cycle of curves has no build order, so where every other handle becomes the object itself, a member is the one reference written after it is built: once, by Build(EvaluationContext). The link is shared by every copy of the member (EnableExtrapolation<T>(T, bool) returns a copy), so an index built on a copy taken before Build prices after it.

Before Build, a member answers its reference date and day counter, both given when it is created, and the times they measure (TimeFromReference(Date)), and refuses every query that needs its curve, "multicurve member not built". After Build, a query is checked against the member's own range and extrapolation flag, then forwarded to the curve it is linked to with extrapolation allowed, so the member's flag rules; its calendar, settlement days and jumps are that curve's. Build links it only to a curve with its reference date and day counter, since it measures a date's time from its own reference date with its own day counter and the curve reads that time against its own; so its day counter is the one it was created with, before Build and after.

Build writes the members' working state while their handles are linked, so no other thread may read a member during Build; once built, a member is immutable, as its curve is.
